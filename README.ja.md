# opencode-novel-plugin（日本語長編小説版）

OpenCode 向けの執筆支援プラグインです。日本語の長編小説を、作品コンセプトから完成原稿まで工程に分けて書き進めるための道具をまとめています。

8つのツール、3つの agent、5つの skill、11のコマンド、16のRTCOプロンプト、16の文書雛形で構成されています。

> **このリポジトリは fork です。**
> 原作は [wmzy/opencode-novel-plugin](https://github.com/wmzy/opencode-novel-plugin)（中国語・中国のWeb小説向け）です。
> 本リポジトリは **2026年10月9日**に、日本語の長編小説執筆向けへ全面的に書き直したものです。
> 変更の内容は「[上流との差分](#上流との差分)」に、ライセンス上の表示は「[ライセンス](#ライセンス)」にあります。

## 何ができるか

- **工程に分けて進める** — 思いつきをログラインに変え、世界観と人物を組み、三幕構成でプロットを引き、シーンに割り、1章ずつ本文を書く。各工程に確認項目があり、前の工程の成果が次の工程の入力になります
- **資料を自動でそろえる** — 章を書く前に `novel_context` を呼ぶと、その章のプロット、登場人物とその現在の状態、これまでのあらすじ、前章の末尾、伏線の確認が優先度つきで返ります
- **AI くさい文章を避ける** — 日本語の AI 生成文に実際に現れる癖を一覧にし、代わりにどう書くかを示します
- **日本語の表記を守る** — 会話の `「」`、三点リーダ `……`、ダッシュ `――`、感嘆符・疑問符のあとの全角スペース、段落頭の字下げを規約として持ち、原稿の点検でも確かめます
- **記録を残す** — 人物の状態、これまでのあらすじ、伏線を章ごとに更新し、長編でつじつまが崩れるのを防ぎます
- **文字数を正しく数える** — 本文だけを、空白と改行を除いた全文字数で数えます。仮名も約物も1文字として数え、ルビと傍点は記法を外して親文字だけを数えます。原稿用紙の枚数は改行で余るマスや字下げがあるので文字数÷400とは一致しません。枚数が要るときは書式を指定すると別に出します（「原稿用紙換算」）。章見出しの行は数に入れないので、保存時の報告と進行状況の数が一致します

## 導入

### npm から

```json
{
  "plugin": ["opencode-novel-plugin-ja"]
}
```

### ローカルのパスから

OpenCode プロジェクトの `opencode.json` に書きます。

```json
{
  "plugin": ["file:///path/to/opencode-novel-plugin"]
}
```

### プラグインディレクトリに置く

次のいずれかにリポジトリを置きます。

- `.opencode/plugins/` — プロジェクトごと
- `~/.config/opencode/plugins/` — 全体

## はじめかた

### 1. モデルを決める

プラグインはモデルを決めません。3つの agent（`novel-planner` / `novel-writer` / `novel-editor`）は、
OpenCode の画面で選んでいるモデルをそのまま使います。途中でモデルを切り替えれば、切り替えたモデルで動きます。

```json
{
  "plugin": ["file:///path/to/opencode-novel-plugin"]
}
```

agent ごとにモデルを固定したいときだけ、`opencode.json` の `agent` に書きます。書いた agent に切り替えると、そのモデルに切り替わります。

```json
{
  "agent": {
    "novel-writer": { "model": "プロバイダ/モデル名" }
  }
}
```

> 企画の工程（temperature 0.3）と原稿の点検（0.1）は確実さが要るので能力の高いモデルを、
> 本文の執筆（0.7）は分量が出るので費用と相談して選ぶとよいです。

### 2. プロジェクトを作る

```
/novel-init
```

タイトル・ジャンル・分量・視点を順に聞かれます。答えると `.novel/` 以下に雛形が一式できます。

### 3. 工程を進める

```
/novel-concept → /novel-world → /novel-characters → /novel-outline → /novel-scenes
```

各工程で、まず例を見せられ、選択肢から選んでいくと文書が埋まります。

### 4. 本文を書く

```
/write-chapter 1
/write-chapter 2
...
```

### 5. 原稿を見る

```
/novel-review 1
/novel-review all --focus=typography
```

### 迷ったら

```
/novel          # いまどこまで進んでいるか、次に何をするかを案内します
/novel-status   # 進行状況の詳細
```

## 執筆の工程

```mermaid
graph LR
    A[コンセプト] --> B[世界観]
    B --> C[登場人物]
    C --> D[プロット概要]
    D --> E[章別プロット]
    E --> F[シーン設計]
    F --> G[本文]
    G --> H[記録の更新]
    H --> G
```

| 工程 | 文書 | プロンプト | やること |
|---|---|---|---|
| 0 | `concept.md` | `concept` | 思いつきを物語の核にする |
| 1 | `world-building.md` | `world-building` | つじつまの合う世界を作る |
| 2 | `characters/profiles.md` | `characters` | 生身の手ざわりのある人物をそろえる |
| 3（段A） | `outline-brief.md` | `outline-brief` | 三幕構成の骨を組む |
| 3（段B） | `outline-detailed.md` | `outline-detailed` | 章ごとの計画に落とす |
| 4 | `scenes.md` | `scenes` | 章をシーンに割る |
| 5 | `chapters/*.md` | `chapter-write` / `chapter-continue` | 1章ずつ書く |

プロット概要は三幕構成で骨を組み、起承転結を別の物差しとして見直します。三幕の幕と起承転結は一対一に対応させません。
起承転結の「転」は危機や山場のことではなく、それまでの見方を変えるもの（別の視点、隠れていた事実など）が入るところだからです。
置く位置は作品ごとに違い、中盤の転換と重なることも、終盤の明かしと重なることもあります。

**進行段階の判定について**：`novel_init` は `concept.md` / `world-building.md` / `characters/profiles.md` を雛形として先に作ります。
そのためこの3つは、ファイルがあるかどうかではなく、**雛形の角括弧プレースホルダ（`[…]`）が残っていないか**で記入済みを判断します。
`novel_status` では **✅ 記入済み / 📝 雛形あり・未記入 / ⬜ 未作成** の3状態で表示されます。

### 短編

`novel_init` に `form: "short"` を渡すと短編の作りになります（`/novel-init` で分量に「短編」を選ぶと、そう呼ばれます）。
長編の作りを縮めるのではなく、工程と骨組みを変えます。中編は長編の作りのまま、章を減らして書きます。

```
コンセプト → 登場人物 → プロット概要（序破急） → シーン設計 → 本文
```

- **世界観と章別プロットの工程を省きます**。舞台はコンセプトに数行書けば足ります（`/novel-world` で作ることもできます）。シーン一覧はプロット概要から直接割ります
- **既定は章なし**（1本の本文。内部では第1章1つで、シーンIDは 1.1、1.2、…）。`chapterCount` を渡せば数章に分けられます。章を分けない短編は `/write-chapter` を番号なしで呼べます
- **プロット概要は序破急で組みます**（プロンプト `outline-short`）。`novel_context` は章別プロットの代わりに、このプロット概要を資料に載せます（枠は `limits.outlineBrief`）
- **書き出し**では、章が1つなら章見出しを付けず、2つ以上なら「一」「二」（タイトルがあれば「一　タイトル」）にします

**序破急**は雅楽の楽曲構成に始まり、世阿弥が能に取り入れた緩急の原理です（『花鏡』）。

| | すること | 速さ | 割合の目安 | 三幕構成では |
|---|---|---|---|---|
| 序 | 人物と状況を平明に置き、問いを一つ置く | ゆるやか | 約2割 | 第一幕 |
| 破 | 序を破り、細部を重ねてずれを広げる | 少しずつ上がる | 約6割 | 第二幕 |
| 急 | 山場と決着。主人公の選択 | 速く、短く | 約2割 | 第三幕 |

割合は目安で、決まりではありません。**「破」は山場ではありません**。破は山場へ向かって速さを上げるところで、山場と決着は「急」の中に来ます。
世阿弥は「一切の事に序破急あり」と書いており、長編でも章や場面の緩急を見直す物差しとして使えます（`novel-writing` skill の「序破急で場面を見直す」）。長編の骨組みは三幕構成のままです。

### 連載（結末未定）

Web 連載（カクヨムなど）のように、結末やエピローグを決めないまま書き進めるなら、`novel_init` に `serial: true` を渡します
（`/novel-init` で中編以上を選ぶと、結末まで決めるか、連載で先は決めないかを聞かれます。あとから `config.json` に `"serial": true` を書き足してもかまいません）。

- **章数と目標文字数は目安**です。予定の章数に達しても完結にならず、超えて書いても状況表示や記録は崩れません。延ばすなら `config.json` の `chapterCount` を直します
- **完結はエピローグで決まります**。`chapters/epilogue.md` があれば完結です。エピローグを置かずに閉じるなら `serial` を外せば、予定章数で判定します
- **結末は「方向だけ」か「未定」でかまいません**。プロット概要は当面の山場（その巻・その部の山）までを三幕で組み、章別プロットは最初の山までで書きはじめ、続きを `outline/chapter-NNN.md` に1章ずつ足します。章別プロットの無い章で `novel_context` を呼ぶと ⚠️ で知らせます
- 伏線は回収の章を決めずに張れます（`targetChapter` を省くと「回収の章は未定」）

連載でない作品でも、予定章数を超えて書くことはできます。エピローグの伏線の回収章は本文のある最後の章として残り、部の範囲も書いた最後の章まで示します。

## ツール

### `novel_init` — プロジェクトを作る

| 引数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `title` | string | ✅ | 作品タイトル |
| `genre` | string | ✅ | ジャンル（現代ドラマ、ミステリ、異世界ファンタジー、時代小説、SF、ホラー、恋愛、青春、ライト文芸など） |
| `targetWords` | number | | 目標総文字数。既定 **120,000**（文庫1冊相当） |
| `chapterCount` | number | | 予定章数。既定 **40**（1章 3,000文字） |
| `theme` | string | | 作品テーマ |
| `narrativePerspective` | string | | 視点。既定 **「三人称一元視点」** |
| `form` | enum | | `long`（既定。中編・長編）／ `short`（短編。下の「短編」）。短編の既定は 20,000文字・章なしで、`world-building.md` を作らない |
| `style` | enum | | 文体の寄せ方。`light`（既定。ライトノベル・Web 小説寄り）／ `literary`（文芸寄り。時代小説・純文学向き）。下の「文体の寄せ方と数字」 |
| `serial` | boolean | | 連載（結末を決めずに書き進める）なら `true`。章数は目安になり、エピローグを書いたら完結（下の「連載（結末未定）」） |
| `martialArtsSetting` | boolean | | 流派・刀剣・剣術の設定ファイルを作るか。省略時はジャンルから判断 |

作られるもの:

```
.novel/
├── config.json            # 作品設定（limits を含む）
├── concept.md             # 作品コンセプト
├── world-building.md      # 世界観
├── characters/
│   ├── profiles.md        # 登場人物の一覧
│   └── state.json         # 登場人物の状態（章・節ごとの変化）
├── summary.md             # これまでのあらすじ
├── foreshadow.json        # 伏線
├── reality-source.md      # 取材メモ
└── chapters/              # 本文（執筆時に自動で作られます）
```

`martialArtsSetting` が有効なときは `wuxia/sects.md` / `wuxia/martial-arts.md` / `wuxia/weapons.md` も作られます。

### `novel_status` — 進行状況

| 引数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `detailed` | boolean | | 章ごとの文字数まで出すか |
| `manuscript` | string | | 原稿用紙の書式（`20x20` のように字数×行数）。指定すると原稿用紙換算の枚数も出す。省くと `config.json` の `manuscript`（下の「原稿用紙換算」） |

返るもの：タイトルとジャンル、目標文字数、視点、現在の工程、工程ごとの進み具合、シーンの進捗、執筆済みの文字数と1章平均、伏線の内訳、次にやること。

本文の集計は章ファイル（`chapters/chapter-NNN.md`）だけを対象にし、章数・累計・1章平均・分量の不足表示に
同じ集計値を使います。`chapters/` に置いた推敲メモなど章ファイル以外の `.md` は数えず、数えていないことを示します。
読み込めない章は累計と平均に含めず、その章を示します。そのときの章数は
「章ファイル 3章 ／ 集計できた本文 2章」のように分けて表示します（章ファイルの数は工程の判定に使う数と同じ）。

### `novel_save_chapter` — 章を保存する

| 引数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `section` | enum | | `chapter`（既定）／ `prologue` ／ `interlude`（幕間）／ `epilogue`（下の「プロローグ・幕間・エピローグ・部」） |
| `chapterNumber` | number | （章と幕間で ✅） | 章番号（1から）。幕間では幕間を置く位置（直前の章の番号） |
| `interludeIndex` | number | | 幕間のとき、同じ章のあとの何番目か。既定 1 |
| `title` | string | ✅ | 章タイトル |
| `content` | string | ✅ | 本文（章見出しの行は含めない） |
| `updateState` | boolean | | 記録更新の案内を出すか。既定 true |

- ファイル名は `chapter-001.md`、`chapter-002.md`、… と自動で連番になります。節は `prologue.md`、`interlude-005-1.md`、`epilogue.md`
- 幕間を置く位置の章がまだ無いときは、保存したうえで ⚠️ で知らせます
- `config.json` に `manuscript` を書いていれば、文字数に添えて原稿用紙換算の枚数を出します（書いていなければ出しません）
- すでにある章を保存し直すと、前の原稿を `.novel/drafts/chapter-001-20261031-153012.md` のように日時つきで残してから上書きします。内容が前と同じなら残しません。いまの章ファイルを読み込めないときは、前の原稿を残せないので保存しません
- 先頭に `# 第N章 タイトル` が付きます（算用数字。機械的に章番号を取り出せるようにするため）
- 文字数は**本文だけ**を、空白と改行を除いた全文字数で数えます。先頭に付く `# 第N章 タイトル` の見出し行は数に入れません（`novel_status` の集計も同じ規則なので、両者の数が一致します）
- 本文に章見出しの行が混ざって渡された場合は取り除いてから保存します（見出しが二重にならないようにするため）
- `title` に改行・タブ・制御文字が含まれていた場合は、半角空白にまとめて**1行に直してから**見出しに書きます。見出しが2行以上になると2行目以降が本文として数えられてしまうためです。直した場合は保存の報告に伝えます。日本語のタイトルで使う全角スペース（「雨の駅　再会」）はそのまま残します

### `novel_context` — 執筆用の資料をそろえる

| 引数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `section` | enum | | `chapter`（既定）／ `prologue` ／ `interlude`（幕間）／ `epilogue`（下の「プロローグ・幕間・エピローグ・部」） |
| `chapterNumber` | number | （章と幕間で ✅） | 章番号（1から）。幕間では幕間を置く位置（直前の章の番号） |
| `interludeIndex` | number | | 幕間のとき、同じ章のあとの何番目か。既定 1 |
| `sceneId` | string | | シーンID（1.1、2.3 など）。渡すとそのシーンに印が付きます |
| `includePrompts` | boolean | | 末尾に「書くときの条件」（分量・視点・書き出しか続きか）を付けるか。既定 true。表記と言い回しは `novel-writing` skill を参照する |

優先度をつけて返します。

| 優先度 | 内容 |
|---|---|
| **P0** | この章のプロット、この章のシーンと `_Prompt` |
| **P1** | 登場人物（一覧＋この章に出る人物の個別設定）、ことばづかいの一覧、その現在の状態、前章の末尾 |
| **P2** | これまでのあらすじ、伏線の確認 |

第2章以降は前章の末尾が付きます。分量は `config.json` の `limits.previousChapterTail` で変えられます（既定 1,200文字）。

**登場人物の絞り込み** — 一覧（`characters/profiles.md`）に加えて、`characters/{キャラクター名}.md` のうち**この章に出る人物の設定だけ**を載せます。この章のプロットとシーンに名前が現れたかどうかで判断します。

照合は二段で行います。まず2文字以上の手がかり（フルネーム、姓、名、呼称）で照合し、当たらなかった人物だけを1文字の手がかり（「林美咲」の「林」のような一文字姓）でもう一度照合します。一段目で誰かが当たっても二段目を省きません。省くと姓の推定に失敗した人物が落ちるためです。

推定に頼りたくないときは、人物設定に**呼称**を書いてください。そこに書かれた語がそのまま手がかりになります。

```markdown
- **呼称**：教頭、鏡味先生
```

誰も特定できなければ全員を載せます（資料が足りないより多いほうが害が小さいため）。
雛形のまま書き換えていない呼称の行（記入例の「森田、先生」）は手がかりにしません。

**ことばづかいの一覧** — この章に出る人物について、人物設定の `## ことばづかい` にある一人称・二人称・丁寧さの基本と、
`### 相手ごとの呼び方` の表を抜き出し、「🗣️ ことばづかい」として別に載せます。人物設定の全文が枠で切られても、この一覧は残ります。
書く章より前に変わったもの（`state.json` の `speech` の `firstPerson` / `addressTerms`）を上に重ね、変わった章を添えます。

```markdown
## ことばづかい

- **一人称**：職員室では「私」、柳井の前では「俺」
- **二人称**：生徒には「君」
- **丁寧さの基本**：教頭と保護者には敬語

### 相手ごとの呼び方

| 相手 | 呼び方 | 丁寧さ | 変わるとき |
|---|---|---|---|
| 杉本千尋 | 杉本 | ため口 | |
| 鏡味征一 | 教頭 | 敬語 | |
```

**分割保存に対応** — 次のどちらの保存のしかたでも読みます。扱いは資料によって二通りです。

| 資料 | 統合ファイル | 章ごと・項目ごとの分割 | 両方ある場合 |
|---|---|---|---|
| 章別プロット | `outline-detailed.md` | `outline/chapter-002.md` | **分割を使う** |
| シーン一覧 | `scenes.md` | `scenes/chapter-002.md` | **分割を使う** |
| 一人ずつの人物設定 | `characters/profiles.md`（一覧） | `characters/{キャラクター名}.md` | 両方を載せる |
| 流派・勢力 | `wuxia/sects.md` | `wuxia/sects/{流派名}.md` | 両方を載せる |
| 剣術・技 | `wuxia/martial-arts.md` | `wuxia/martial-arts/*.md` | 両方を載せる |
| 刀剣 | `wuxia/weapons.md` | `wuxia/weapons/{刀剣名}.md` | 両方を載せる |
| 取材メモ | `reality-source.md` | `reality/events/`、`reality/archetypes/`、`reality/mappings/` | 両方を載せる |

章別プロットとシーン一覧は**その章の記述が一箇所に収まる**ものなので、分割があればそちらだけを使います。
設定の資料は**統合ファイルを概観として残したまま項目ごとに分ける**使い方ができるため、両方を載せます（人物の一覧と個別設定と同じ扱いです）。どのファイル由来かは見出しで示されます。

**文字数の枠の配分** — 複数のファイルから集めた資料は、`limits` の枠を**短いものから順に満たす形で配分**します。連結してから先頭で切ると、前に置いたファイルが長いだけで後ろのファイルが丸ごと落ちるためです（人物一覧が長いと個別設定が一件も入らない、など）。

`sceneId` で指定したシーンには**先に枠を配り**、残りを他のシーンに配ります。全部を同列に扱うと、単独なら上限に収まる長さでも他のシーンと同じ分しかもらえず、`_Prompt` の末尾（`Success` など）が切れて手引きとして使えなくなるためです。

枠が回らず落ちたファイルは、名前だけを残して落ちたことが分かるようにします。

**シーン進捗の集計** — `novel_status` のシーン進捗は、統合ファイルと分割の両方から集めます。ただし**同じ章が両方にある場合は分割側だけを数えます**。分割へ移したあとも統合側に古い記述が残っていると二重に数えてしまうためです（分割側で完了にしたシーンが、統合側の未着手と合わせて 1/2 になる）。ID の重複を取り除くだけでは、分割時に統合側から削除したシーンが残っていると数に入ってしまうので、章ファイルがある章は統合側をまるごと除きます。

**章ファイルと認める名前** — 章ごとの分割ファイルとして扱うのは、`scenes/` や `outline/` の**直下**にある **`chapter-<数字>.md`** だけです。

| 名前 | 扱い |
|---|---|
| `scenes/chapter-002.md` | ✅ 章ファイル |
| `scenes/chapter-2.md` | ✅ 章ファイル（ゼロ埋めの桁数は問いません） |
| `scenes/backup-chapter-002.md` | ❌ 章ファイルではない |
| `scenes/chapter-002.md.bak` | ❌ 同じ |
| `scenes/old/chapter-002.md` | ❌ 同じ（直下ではないため） |
| `scenes/メモ.md` | ❌ 同じ |

読み込み・存在判定・集計の除外判定が**すべて同じ条件**を使います。条件がずれると、読み込みでは使わないファイルを根拠に統合ファイルを集計から外してしまい、執筆資料と進捗が食い違います（控えを置いただけで進捗が古い側を指す、など）。

このため、控えや覚え書きを `scenes/` に置いても、集計には入らず現行の統合ファイルも外されません。一方で、決めた置き場所以外のファイル（`scenes/メモ.md` など）はシーン進捗に数えられません。

章別プロットから該当章を取り出すとき、見出しの章番号は**算用数字・全角数字・漢数字のいずれでも読み取ります**（`## 第2章` でも `## 第二章` でも拾えます）。シーンは `章番号.連番` の ID で選び分けます。

進行段階の判定（`determinePhase`）と `novel_status` の工程表示・シーン進捗も、同じ基準で分割保存を見ます。

### `novel_update` — 記録を更新する

| 引数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `action` | enum | ✅ | `character-state` / `summary` / `foreshadow` / `prompt` |
| `content` | string | ✅ | 人物の状態・伏線は下の形の JSON 文字列。あらすじはその章のあらすじ |
| `section` | enum | | プロローグ・幕間・エピローグの記録のとき `prologue` ／ `interlude` ／ `epilogue` |
| `chapterNumber` | number | | 対象の章番号。1以上の整数（あらすじと人物の状態では必須。プロローグ・エピローグを除く）。幕間では直前の章 |
| `interludeIndex` | number | | 幕間のとき、同じ章のあとの何番目か。既定 1 |

形を確かめてから保存します。1か所でも外れていれば**何も書き込まず**、どこが違うかと正しい形の例を返します
（使えないキー、日本語の `status`、空の `changes` など）。成功したときは、実際に変えた項目を人物ごとに返します。
以前は形を確かめずに保存しており、`"回収済み"` のような状態や `state` / `inner` のような
知らないキーを受け取っても「更新しました」と返していました。

**記録ファイルが壊れているとき** — 更新の前に、記録ファイル（`foreshadow.json` / `characters/state.json` / `summary.md`）を
読み直して確かめます。読み込めない、JSON の構文が壊れている、形が違う（`{"items": null}`、名前の無い人物、
文字列になった一覧、読めない節のキーなど）のいずれかなら、**元のファイルに触れずに**更新を断り、理由と直し方を返します。
空の記録とみなして続けると、壊れたファイルを新しい内容だけで上書きし、それまでの記録が消えるためです。
ファイルが無いだけなら、新しく作ります。`novel_status` と `novel_context` も、壊れた記録を「0件」や
「記録なし」と区別して知らせます。伏線の項目ごとの不正（日本語の `status` など）は断らず、渡し直して直せます。

**あらすじの更新** — `summary.md` は章ごとの節（`## 第N章 タイトル`）で持ちます。
渡すのは**その章の分だけ**で、同じ章の節だけが差し替わり、前の章の節は残ります。
見出しを省くと、保存済みの本文から章タイトルを取って付けます。
content を `## 全体の流れ` で始めると、物語全体の要約だけを差し替えます。このときの `chapterNumber` は
「何章までの要約か」で、見出しに `## 全体の流れ（第N章まで）` として残ります。

`novel_context` は、書こうとしている章より前の節を**直前の章から**順に `limits.summary` の枠へ詰め、
入りきらない古い章から落とします（落ちた範囲は明記し、筋は「全体の流れ」で補う）。
「全体の流れ」と旧形式の記述には枠の3分の1までを先に取っておきます。記録の無い章があれば知らせます。

書こうとしている章以降の内容は載せません（前の章を書き直すときに先の出来事が混ざらないように）。

| 記述 | 何章までの要約とみなすか | 載せる条件 |
|---|---|---|
| `## 第N章` の節 | 第N章 | N が書く章より前 |
| `## 全体の流れ（第N章まで）` | 第N章 | N が書く章より前 |
| 範囲の無い `## 全体の流れ`（手で書いたもの） | 記録のある最後の章 | 同上 |
| `## 以前の形式のあらすじ（第N章まで）` | 第N章 | 同上 |
| まだ移していない旧形式の記述（`## 物語の進み` など） | 記録のある最後の章 | 同上 |

旧形式の記述（章の節にする前に、全体を書き直していたころのもの）は消しません。
`novel_update(summary)` が初めて書き込むときに `## 以前の形式のあらすじ（第N章まで）` の節へ移し、
範囲を見出しに**固定**します。N は次のうち最も大きいものです。

- その時点で本文のある最後の章
- 移す前のあらすじにある章の節の最大章番号（本文を退避・削除していても、ここで拾える）
- 差し込む章の直前の章

読み込むたびに推定すると、過去の章の節を足しただけで範囲が縮み、先の出来事が資料へ混ざるためです。

**人物の状態の更新（JSON）**

この章・節で変わった人物と、変わった欄だけを渡します（`chapterNumber` か `section` が必須）。

```json
{
  "updates": [
    {
      "name": "森田悠",
      "changes": {
        "physicalState": "右手に軽い切り傷",
        "mentalState": "動揺を隠している",
        "attributes": { "現在地": "職員室" },
        "lists": { "持ち物": { "added": ["杉本の作文"] } },
        "relationships": { "相田可奈": "信用に揺らぎが出た" },
        "speech": { "addressTerms": { "杉本千尋": "千尋（この章から名前で呼ぶ）" } },
        "events": ["名簿の印の違いに気づいた"]
      }
    }
  ]
}
```

| キー | 中身 |
|---|---|
| `status` | `active` / `deceased` / `missing` / `retired` |
| `physicalState` / `mentalState` | 体と心の状態 |
| `attributes` | `{ 項目: 値 }`。現在地・服装・所属など、作品に合わせて項目名を決める |
| `lists` | `{ 一覧の名前: { added, removed } }`。持ち物・できること・手がかりなど |
| `relationships` | `{ 相手: 関係 }` |
| `speech` | `{ firstPerson, addressTerms: { 相手: いまの呼び方 } }`。人物設定から変わったときだけ |
| `events` | この章・節の出来事 |

値に `null` を渡すと、その欄を消します。

`state.json` には、章・節ごとの**変化だけ**が残ります（`{ "sections": { "chapter-001": { "updates": [...] } } }`）。
`novel_context` は、書く章より前の変化を読む順番に重ねて、その時点の状態を組み立てます。
前の章を書き直すときに、先の章の出来事（死亡や入手した品）が資料に混ざりません。

- 同じ章に送り直すと、その章の変化に重なります。章を書き直したときは `"replace": true` を添えて、その章の変化を置き換えます。後の章の資料にもそのまま反映されます
- 誰も変わらなかった章・節は `{"updates": []}` を渡して記録します。`novel_status` は、本文があるのに記録の無い章・節を知らせます
- 新しい項目名（`attributes` / `lists`）を使うと、すでに使っている項目名を添えて知らせます（「持ち物」と「所持品」のような揺れを防ぐため）。資料と更新用プロンプトにも、使っている項目名が載ります

資料の「🔄 登場人物の現在の状態」では、この章のプロットとシーンに名前が出る人物を上に詳しく、ほかの人物を下に1行で並べます。
死亡・行方不明・退場は名前の横に、変わった章とともに示します（例：`**ドルガ**【死亡（第2章）】`）。出来事は章のラベルを付けて直近5件までです。

**伏線の更新（JSON）**

```json
{
  "items": [
    {
      "id": "F1",
      "title": "九月に出されなかった作文",
      "content": "名簿には提出済みの印があるが、本文が存在しない",
      "category": "mystery",
      "status": "planted",
      "plantChapter": 1,
      "targetChapter": 40
    }
  ]
}
```

伏線の状態は次のように移ります。

```
pending → planted → resolved
                  → abandoned
```

**知らせ方** — `novel_context` が章ごとに伏線を知らせます。知らせるかどうかは状態と回収予定で決まります。

| 状態 | 回収予定 | 知らせるか |
|---|---|---|
| `resolved`（回収済み） | — | ❌ 知らせない |
| `abandoned`（取り下げ済み） | — | ❌ 知らせない |
| `planted`（張り済み） | 未定・先・この章・過ぎた | ✅ **常に**知らせる |
| `pending`（未着手） | 過ぎた | ✅ 知らせる |
| `pending` | この章 | ✅ 知らせる |
| `pending` | 3章以内 | ✅ 知らせる |
| `pending` | 4章以上先 | ❌ 知らせない |
| `pending` | 未定 | ❌ 知らせない |

言い換えると、**回収済みと取り下げ済みは知らせません。未着手の伏線は、回収予定が未定か3章より先なら知らせません。張り済みは回収予定にかかわらず知らせます。** 終わった伏線を知らせると済んだものをもう一度回収しようとしてしまい、未着手の遠い伏線を毎章並べるといま扱うべきものが埋もれるためです。章数は `src/constants.ts` の `FORESHADOW_LOOKAHEAD` です。

知らせるものには、急ぎぐあいに応じた印と添え書きが付きます。

| 状況 | 印 | 添え書き |
|---|---|---|
| 回収予定の章を過ぎている | ⚠️ | 回収予定の第N章を過ぎています |
| この章が回収予定 | 🎯 | ← この章で回収 |
| 回収予定が先にある | ⏰ | 第N章で回収予定 |
| 記録の形が崩れている（日本語の status など） | ❓ | 状態を判定できない。直すよう促す |

形の崩れた記録は、回収済みのものを「未回収」と誤って知らせないよう、状態の判定から外して別に並べます。
保存済みの記録も入力と同じ基準で確かめます（`id`・`title`・`content`・`status` の欠落、使えないキー、
`"targetChapter": "十二"` のような型の誤り）。`id` を指して正しい値を渡し直すと直ります。

以前の保存で入った独自のキー（`detail` など）は、通常の更新では**残します**。そこにしか書かれていない
内容があるためです。中身を `content` や `notes` に移したうえで、`"removeKeys": ["detail"]` を添えたときだけ外します。

`status: "resolved"` を渡して `resolvedChapter` を省くと、回収した章を `chapterNumber` で補います。
補うのは、その更新で**回収済みに変わったとき**だけです。すでに回収済みのものに同じ状態を伝え直しても、
記録済みの回収章は変えません（変えるときは `resolvedChapter` を明示します）。

人物の状態と伏線の更新は、更新前と比べて**実際に変わったもの**を報告します。持っている品の追加や
同じ値の入れ直しは変化に数えず、何も変わらなければファイルを書かずに `ℹ️` で返します
（人物の状態は、その章・節を書き終えた時点の状態で比べます。記録の無かった節は、変化が無くても記録済みにします）。
| 回収の章が未定 | 🌱 | 回収の章は未定 |

並び順は急ぐものから。過ぎたものどうしは予定が古い順です。添え書きには「張り済み」か「まだ張っていません」も付きます（張る前に回収しようとしないため）。

### `novel_check` — 表記を点検する

| 引数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `section` | enum | | 点検する節の種類。省くと `chapterNumber` の章 |
| `chapterNumber` | number | | 点検する章（幕間なら直前の章）。`section` も省くと書いた章と節すべて |
| `interludeIndex` | number | | 幕間のとき、同じ章のあとの何番目か。既定 1 |
| `maxIssues` | number | | 1章あたりに並べる箇所の上限。既定 30（件数は上限に関わらずすべて数える） |

表記規約（`novel-writing` skill が正本）のうち、機械で確かめられるものを点検し、行と字の位置つきで返します。
保存のたびに `novel_save_chapter` の報告にも件数と最初の数箇所が出ます。

| 規則 | 重さ | 拾うもの |
|---|---|---|
| ルビ・傍点の記法 | ❌ | 《》が無い `｜`、行の中で閉じない《 や《《、空のルビ、傍点の中のルビ |
| 括弧の対応 | ❌ | 行の中で閉じない「」『』（括弧の中では改行しない）、対応の無い閉じ括弧 |
| 会話文末の句点 | ❌ | `「行こう。」` |
| 三点リーダ | ❌ | 奇数個の `…`、`‥`、`・・・`、`...` |
| ダッシュ | ❌ | 奇数個の `―`、`—`（U+2014）、`─`、長音符の連なり `ーー`（カタカナ語の長音は除く） |
| 三点リーダ・ダッシュのあとの空白 | ❌ | `……　` |
| 半角の約物 | ❌ | `!` `?` |
| 感嘆符・疑問符のあとの空白 | ❌ | 直後に全角スペースが無い、半角スペース、2つ以上の空白、閉じ括弧の直前・行末・約物の前（`「待て！　……」` `「何！　？」`）の空白。閉じ括弧の直前・行末・約物の連続（`！？` など）では空けない |
| 段落頭の字下げ | ❌ | 地の文の字下げなし、会話行や三点リーダ・ダッシュで始まる行の字下げ。2字以上の字下げは ⚠️。区切りの記号だけの行（`＊` など）は見ない |
| 全角の算用数字 | ❌ | `０`〜`９` |
| 地の文の算用数字 | ⚠️ | 会話の外の算用数字。文芸寄り（`style: "literary"`）の作品のときだけ見る（年号・型番など意図したものなら残してよい） |
| 日本語と英数字のあいだの空白 | ⚠️ | `昨日 iPhone を` |

漢数字と算用数字の使い分けが作品の中でそろっているかは、機械では見ません。地の文の算用数字は、文芸寄り（`style: "literary"`）の作品でだけ ⚠️ として拾います。
ルビ・傍点の記法以外の規則は、ルビの読みと記号を外した文で見ます（`｜十七《17》` の読みを地の文の算用数字として拾いません）。字の位置は元の行のものを返します。

### `novel_export` — 原稿を書き出す

| 引数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `format` | enum | | `text`（既定）／ `markdown` |
| `numerals` | enum | | 章見出しの数字。`kanji` ／ `arabic`。既定は text なら漢数字、markdown なら算用数字 |
| `ruby` | enum | | ルビ・傍点の書き出し先の記法（下の表）。既定は text なら `kakuyomu`、markdown なら `html` |
| `manuscript` | string | | 原稿用紙の書式（`20x20`）。指定すると報告に原稿用紙換算の枚数を添える。省くと `config.json` の `manuscript` |
| `fromChapter` | number | | この章から。既定 1 |
| `toChapter` | number | | この章まで。既定は最後の章 |
| `outputPath` | string | | 書き出し先（作品のディレクトリからの相対パス）。既定 `.novel/export/{作品タイトル}.txt`（`.md`） |

書いた章を読む順番に繋ぎます。プロローグ・幕間・エピローグも置かれた位置に繋ぎ、`config.json` に `parts` があれば部の最初の章の前に部の見出し（`第一部　春`）を置きます。本文は書き換えません。

範囲を指定したとき、プロローグは `fromChapter` が1のとき、幕間は直前の章が範囲にあるとき、エピローグは `toChapter` を省いたときに含めます。部の見出しは、部の最初の章が範囲にあるときに置きます。`parts` が読めなければ書き出さずに断ります。

- **text** — 投稿サイトや縦書きのエディタに貼る形。先頭に作品タイトル、章見出しは `第一章　タイトル`（全角スペース区切り）で、Markdown の記号を使いません
- **markdown** — 作品タイトルを `#`、章を `## 第1章 タイトル` にして繋ぎます。部があるときは部を `##`、章と節を `###` にします

**ルビと傍点** — 原稿はカクヨムの記法（`｜親文字《ルビ》`・`《《傍点》》`）で書きます。書き出すときに `ruby` で記法を選べます。

| `ruby` | ルビ | 傍点 |
|---|---|---|
| `kakuyomu` | `｜親文字《ルビ》` | `《《傍点》》` |
| `narou` | `｜親文字《ルビ》` | 1字ずつ `｜傍《・》｜点《・》`（小説家になろうは傍点の記法を持たない） |
| `aozora` | `｜親文字《ルビ》` | `傍点［＃「傍点」に傍点］`。括弧の《》は `※［＃始め二重山括弧、1-1-52］` に直す |
| `pixiv` | `[[rb:親文字 > ルビ]]` | 1字ずつ `[[rb:傍 > ・]]` |
| `html` | `<ruby>親文字<rt>ルビ</rt></ruby>` | 1字ずつ「・」のルビ |
| `paren` | `親文字（ルビ）`（応募原稿などで括弧書きを求められるとき） | 外す |
| `none` | 親文字だけ | 外す |

文字数は、どの記法でも親文字だけを数えます（`novel_save_chapter` / `novel_status` と同じ）。

本文の無い章は飛ばして、報告で知らせます（`toChapter` を指定したときは、その章までの欠けを見ます）。
表記の規約違反が残っていれば、その件数も添えます。読み込めない章が1つでもあれば、何も書き出さずに断ります
（空の本文として繋ぐと、章が欠けたまま書き出してしまうため）。

書き出し先は作品のディレクトリの中に限り、`.novel/chapters/` には書き出しません（章ファイルと混ざるため）。
シンボリックリンクを経由した書き込みも防ぎます。書き出し先そのものがリンクなら断り、親ディレクトリは実体をたどって判定します。

`novel_check` も、読み込めない章は「問題なし」とせず、点検できなかった章として示します。

## 表記規約

`novel-writing` skill が正本です。要点を挙げます。

### 会話
- 会話は `「」`、会話中の引用や作中の本は `『』`
- **会話文末に句点を打たない**（○ `「行こう」` / × `「行こう。」`）
- `「」` の中では改行しない

### 三点リーダとダッシュ
- 三点リーダは **`……`**（U+2026 を2つ）。単独の `…` や3つ重ねは使わない
- ダッシュは **`――`**（U+2015 を2つ）。`—`（U+2014）や `ー`（長音符）で代用しない
- 直後に全角スペースを入れない

### 感嘆符・疑問符
- 全角 `！` `？` を使う。重ねや組み合わせ（`！！` `！？` `？！`）は使ってよい
- **直後に全角スペース1つ**（○ `「待て！　行くな」`）
- ただし次は入れない — 閉じ括弧の直前（○ `「待て！」`）、行末、約物が連続するとき（○ `「どこだ！？」`）

### 段落
- 段落頭は全角スペース1字下げ
- `「` で始まる会話行、三点リーダ・ダッシュで始まる行は字下げしない

### ルビと傍点
- ルビは **`｜親文字《ルビ》`**、傍点は **`《《傍点》》`**（カクヨムの記法）。1行の中で閉じる
- 漢字だけの親文字なら ｜ を省ける（`東京《とうきょう》`）。漢字の直後にルビでない《》を置くときは `｜《`
- 文字数は親文字だけを数える。書き出すときに、なろう・pixiv・青空文庫・HTML などの記法へ直せる（`novel_export` の `ruby`）

保存のたびに `novel_save_chapter` の報告へ点検結果が出ます。全件は `novel_check` で見られます（下の「ツール」を参照）。

### 文体の寄せ方と数字
`config.json` の `style` で寄せ方を選びます（`novel_init` の引数 `style`）。既定はライトノベル寄りです。

| | ライトノベル寄り（既定） | 文芸寄り（`style: "literary"`） |
|---|---|---|
| 地の文の数 | 単位付きの数・時刻・ステータスは算用数字でよい（3メートル、HP 1200） | 原則漢数字（三日後、十七歳） |
| 空行 | 間やテンポのための1行あけは可 | 場面転換だけ |
| 比喩 | 語り手の軽口・ツッコミは声として可 | 少なめに |

どちらでも、同じ種類の数は作品の中でそろえます。場面転換と視点の切り替えは、区切りの行（`◇` など）で示します（ライトノベル寄りでは空行を間にも使うので、空行だけでは区切りになりません）。同じ場面の中で視点人物は入れ替えません。

### AI くさい文章を避ける

`novel-writing` skill に、日本語の AI 生成文に実際に現れる癖を A〜E の5群で一覧にしています。たとえば次のようなものです。

| 使わない | 代わりに |
|---|---|
| 思わず〜 | 動作をそのまま書く →「口の端が上がった」 |
| 胸が熱くなった／込み上げてきた | 身体の細部 →「鼻の奥が痛くなって、襟を直すふりで顔を伏せた」 |
| その瞬間／次の瞬間 | 動作の連続で時間を示す |
| 目の奥に〜が揺れた | 目の具体的な動き →「目を細めた」 |
| 同じ文末が3文以上続く | 「〜た／〜ている／体言止め」を混ぜる |
| まるで〜のようだった（型の連発） | 型の直喩を続けない。軽口やツッコミの比喩は語り手の声として効くものだけ |

## 取材（現実から題材を取る）

報道・歴史・身近な人から題材を得て、異化（なじみのあるものを見慣れないものに変える処理）を通して小説に入れるための仕組みです。ジャンルを問わず使えます。素材は `.novel/reality-source.md` に残します。

### 三つの手法

| 手法 | 芯になる操作 | 向くもの |
|---|---|---|
| **社会派** | 一人の転落を追いながら、原因が個人ではなく仕組みにあると気づかせる（松本清張・山崎豊子の系統） | 社会の歪みを扱う長編、組織もの |
| **私小説的** | 扱う範囲を狭め、その代わり解像度を上げる | 家族、仕事、病や介護 |
| **寓話・象徴** | 中心に一つだけありえない設定を置き、ほかは現実どおりに書く | 短編、生々しすぎる題材 |

### 異化の技法

視点を替える／時間を変形する／空間を移す／ことばを変える／感覚を替える／寸法を変える／立場を入れ替える／決まりを変える／文化をずらす／貼り合わせる。
それぞれに現代物と時代物の使用例が付いています。

### 人物の型の取り出し

観察する → 動機を見つける → 原型に重ねる（ユングの8原型を日本の物語に合わせたもの）→ 作り変える、の四段です。

### 法律上の注意（日本法）

> ⚠️ ここに書くのは一般的な注意です。実際に公開する前に、扱う素材が微妙なときは法律の専門家に相談してください。

skill には次を収めています。

- **名誉毀損** — 刑法230条、民法709条。真実であることは免れる理由にならない
- **プライバシー権** — 「宴のあと」事件（東京地裁 昭和39年）
- **モデル小説と出版の差止め** — 「石に泳ぐ魚」事件（最高裁 平成14年）。損害賠償ではなく、出す前に止められた
- **パブリシティ権** — ピンク・レディー事件（最高裁 平成24年）
- **作り変えの手順** — 名前・外見・職業と立場・時代か土地・家族構成・出来事の筋道のうち**三つ以上**を変えるところから始める。ただしこれは創作上の手順であって、法的な安全基準ではない
- **「この作品はフィクションです」の一文**
- **著作権（歌詞・詩・ほかの作品を引く）** — 著作権法32条の引用の条件。歌詞は一行でも著作物で、小説では引用と認められにくく、書籍では許諾（JASRAC・NexTone など）を取るのが通例。投稿サイトの包括契約は、そのサイトの中だけの話で書籍化には及ばない
- **特定されるかどうかの見かた** — 本人が気づくかどうかは基準にならない。問われるのは**その人を知っている読者が分かるか**（同定可能性）と、**何を書いたか**（私生活・病・身体的な特徴に触れるほど、わずかな手がかりでも侵害になり得る）

```
│   ├── ...
│   └── epilogue.md          # エピローグ（置くときだけ）
└── drafts/                  # 旧稿（保存し直したときに前の原稿を残す）
```

分量が増えたら分けられます。

- 登場人物：`characters/{キャラクター名}.md`
- 章別プロット：`outline/chapter-001.md`、…
- シーン一覧：`scenes/chapter-001.md`、…
- 流派：`wuxia/sects/{流派名}.md`
- 刀剣：`wuxia/weapons/{刀剣名}.md`
- 取材：`reality/events/`、`reality/archetypes/`、`reality/mappings/`

決めごと：

- すべて UTF-8
- 人が読む内容は Markdown、プログラムが読み書きする内容は JSON
- 本文のファイル名は自動の連番

### プロローグ・幕間・エピローグ・部

どれも**章の数（予定章数）には入りません**。章番号、シーンID、進行段階の判定は章だけで動きます。
文字数の累計・原稿用紙換算・表記の点検・書き出しのように原稿全体を扱うところでは、読む順番に並べて含めます。

| もの | 本文のファイル | 読む順番 | 書くとき |
|---|---|---|---|
| プロローグ | `chapters/prologue.md` | 第1章の前 | `/write-chapter prologue` |
| 幕間 | `chapters/interlude-005-1.md`（第5章のあとの1つ目） | 第5章のあと、第6章の前。同じ章のあとに複数置ける | `/write-chapter interlude 5`（2つ目は `interlude 5 2`） |
| エピローグ | `chapters/epilogue.md` | 最後の章のあと | `/write-chapter epilogue` |
| 部 | ファイルは作らない。`config.json` の `parts` | 部の最初の章の前 | — |

- **プロット**は章別プロットに `## プロローグ` `## 幕間（第5章のあと）`（2つ目は `## 幕間（第5章のあと・2）`）`## エピローグ` の見出しで書くか、`outline/prologue.md` のように分けます。シーンIDは振りません
- **前の本文の末尾**は、読む順番ですぐ前の本文を載せます（第6章の前に幕間があれば幕間、第1章ならプロローグ）
- **あらすじ**は `## プロローグ` などの節として残ります（`novel_update(summary)` に `section` を渡す）。資料には読む順番で前のものだけを載せ、`novel_status` はあらすじの無い節も知らせます
- **伏線**は章番号で記録します。`section` を渡すと、プロローグは 0、幕間は直前の章、エピローグは本文のある最後の章（予定章数を超えて書いていればその章。まだ1章も無ければ予定章数）として記録します
- **人物の状態**は節そのものの変化として記録します（`section` を渡す）。資料には読む順番で前の節までの変化が載ります

部は `config.json` に書きます。章番号は部をまたいで通しです。

```json
{
  "parts": [
    { "title": "春", "fromChapter": 1 },
    { "title": "夏", "fromChapter": 13 }
  ]
}
```

`novel_status` は部ごとに何章まで書けたかを、`novel_context` はその章が何部の何章目かを示します。
形が違えば（番号が昇順でない、題が空など）、`novel_status` で ⚠️ を出し、`novel_export` は書き出さずに断ります。

### 原稿用紙換算

新人賞の応募規定のように、分量を「400字詰め原稿用紙で何枚」と決められているときのための表示です。
`config.json` に書式を書くと、`novel_status`・`novel_save_chapter`・`novel_export` が文字数に添えて枚数を出します。

```json
{
  "manuscript": "20x20"
}
```

書式は「字数×行数」です（`20x20` は400字詰め、`40x30` や `42x34` は応募規定でよく見る書式）。
**書かなければ枚数は一切出ません**。目標文字数・1章平均・分量の不足の判定は、書いても書かなくても文字数で行います（Web 小説のように文字数で書く作品の邪魔をしないため）。
一度だけ確かめたいときは、`novel_status` や `novel_export` の引数 `manuscript` で指定できます（`config.json` より優先します）。

数え方は原稿用紙の書き方に合わせています。

- 段落（ファイルの1行）は新しい行から書きはじめ、段落の最後の行の残りのマスも1行と数える
- 1文字1マス。段落頭の字下げの全角スペースも1マス、「……」「――」は2マス
- 行頭に来る句読点・閉じ括弧は、前の行の最後のマスに収める（ぶら下げ）
- ルビと傍点は記法を外して親文字だけを数える
- **空行は数えない**（段落ごとに空行を入れる Web 小説の書き方で、枚数が膨らまないように）
- 章見出しの行は数えない。章ごとの改ページはせず、全体の行数を1枚の行数で割って切り上げる

文字数を400で割った値より多くなるのがふつうです（会話の多い原稿ほど、行の残りのマスが増えるため）。
応募規定に細かな決まり（章ごとの改ページ、1行アキの数え方など）があるときは、規定に合わせて確かめてください。

### よくある質問

**世界観を途中で変えたい**
`.novel/world-building.md` を直接編集してください。

**工程を飛ばしたい**
順に進めるのが前提ですが、すでに設定ができているなら Edit ツールで対応する文書を直接書いてかまいません。進行状況は文書の内容から判定されます。

**登場人物が増えて state.json が大きくなった**
`state.json` は章ごとの変化だけを持つので、章が進んでも1章あたりの量は増えません。`novel_context` は、この章に出る人物を上に詳しく、
ほかの人物を1行ずつ載せ、`limits.characterState` の枠に入るところまでにします。人物設定のほうは `limits.characterProfiles` の範囲で切り出します。
人物ごとにファイルを分ける（`characters/{キャラクター名}.md`）と扱いやすくなります。

**データをバックアップしたい**
`.novel/` を丸ごとコピーすれば足ります。Git に入れれば履歴も残ります。

**複数の作品を同時に書きたい**
`.novel/` はプロジェクトディレクトリごとに独立しています。別のディレクトリで作業してください。

**1章が目標文字数に届かない／超える**
1章の目安は、目標文字数÷章数（`novel_context` の「この章の目安」）で、振れ幅は ±10% まで見ています。設定が無いときの一般的な目安は1章 3,000〜6,000文字で、山場の章は 8,000文字まで伸ばしてかまいません。

### テストについて

Node 24 標準の `node:test` を使い、**テスト用の依存パッケージはありません**。

### 中国語の残存チェック

`pnpm check:ja`（`scripts/check-japanese.mjs`）が三段で調べます。

判定は**「簡体字であること」を積極的な証拠**にします。「日本語の収録表に無い字形だから中国語」という判定はしません。字形が収録表に無いことは、その字が中国語である証拠にならないからです。たとえば `頰` `剝` `塡` `瘦` はいずれも日本語の正字ですが、CP932 には収まりません。

1. **簡体字の一覧** — 日本語では使われない簡体字 709 字と突き合わせます
2. **中国語式の約物** — 左右の二重引用符、全角カンマ、全角セミコロンなど
3. **日本語の文には現れない中国語の語** — `什么` `没有` `哪里` など 22 語。単独の漢字は使いません（`什` だけを禁じると日本語の `什器` に当たります）

**一覧の作り方**（更新するときは同じ手順を踏んでください）

1. 上流（ローカライズ前）のソース全体に現れた漢字を集める
2. 高頻度の簡体字を足す
3. **JIS X 0213 の収録字をすべて除く**

手順3が肝心です。JIS X 0213 は日本語の文に使う文字を定めた規格なので、収録字は日本語の文書に正当に現れ得ます。収録字を一覧から除いておけば、**第一段（簡体字の一覧）が JIS X 0213 の収録字を誤検知することはありません**。判定には `iconv` を使います。

ただしこれは第一段についての保証です。第二段（約物）と第三段（語）は、日本語の文に現れ得るものを一覧に入れてしまえば誤検知します（実際、`什` を単独で禁じていたため日本語の `什器` を誤検知していました）。この二段は目で選んだ一覧なので、誤検知ゼロが機械的に保証されているわけではありません。

```bash
printf '%s' "<字>" | iconv -f UTF-8 -t EUC-JISX0213 >/dev/null 2>&1
# 成功したら日本語で使う字。一覧に入れてはいけない
```

**限界** — 手順3により、簡体字でありながら JIS X 0213 に収録されている字（`关` `复` `开` `异` `种` `确` `离` `适` など 64 字）は一覧に入りません。それらだけで書かれた中国語の文は第一段では捕まりません。これは意図した取り引きです。CI を止める検査が正しい内容を落とす害のほうが大きいからです。取りこぼしは第二段・第三段が補います。

**検出器そのもののテスト** — `test-src/scripts/check-japanese.test.mjs` が `pnpm test` で走ります。一覧に JIS X 0213 の収録字が混ざっていないことを `iconv` で機械的に検証し（混ざればテストが落ちます）、日本語13ケースが検出されないこと・中国語6ケースが検出されることを確かめます。あわせて CLI も実際に起動して確かめます（`#` や空白や日本語を含むパスでも検査が走ること、終了コードが正しいこと）。`iconv` が `EUC-JISX0213` を扱えない環境では、一覧の検証は空振りさせずにスキップします。`node scripts/check-japanese.mjs --self-test` でも判定表を目で確認できます。

意図的に残す箇所は `ALLOW` に `{ file, contains, reason }` で追記します（行番号指定は編集でずれるため、内容指定を推奨）。
`LICENSE`（AGPL-3.0 の原文）は検査対象に含めていません。
